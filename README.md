# defi-yield-optimizer

複数チェーン/プロトコルの利回り(APY)を横断的に比較し、資金配分を最適化するツール。

## 進め方(段階を踏む)

1. **フェーズ1(今ここ)**: DeFiLlama公開API(`yields.llama.fi`)から読み取り専用でAPYデータを取得・分析。
   ウォレット接続や送金は一切行わない。まずはどのプール/チェーンが安定して高利回りかを
   データで把握する。
2. **フェーズ2(今ここ)**: 過去のAPY推移データを蓄積し、変動リスク(APYの安定性、TVLの増減、
   プロトコルの監査状況・稼働歴・過去のハック有無)を加味したスコアリングモデルを作り、
   単一プール/プロトコルへの集中を避けた配分案を出す。
3. **フェーズ3**: 実際の資金移動・スマートコントラクト操作(入金/出金/スワップ)は
   ユーザー自身のウォレットで実行する。自動化する場合も、まずテストネットや少額での
   検証を挟むこと。秘密鍵はどのコードにもハードコードしない。

## セットアップ

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt
python src/yields.py     # 全プールのAPYスナップショット
python src/scoring.py    # 上位候補の履歴を取得し、安定性・プロトコルリスクを加味してスコアリング+配分案
python src/risk.py       # 監査数/稼働歴/過去のハック有無だけを単体で確認したい場合
python src/backtest.py   # スコアリングの判定に予測力があるかの簡易バックテスト
```

`notebooks/explore_yields.ipynb` を開く場合は、先に `.venv` をJupyterカーネルとして登録すること
(グローバルのPython環境には依存パッケージが入っていないため、既定のカーネルのままだと動かない)。

```bash
.venv/Scripts/python -m ipykernel install --user --name defi-yield-optimizer --display-name "Python (defi-yield-optimizer)"
```

`src/scoring.py` は生APYの平均ではなく中央値を使い、以下に該当するプールはスコア対象から
除外(または大きく減点)する。異常に高いAPYは大抵、報酬トークンの一時的な大量エミッションや
薄い流動性による見せかけであり、そのまま鵜呑みにしないための安全弁。

- 変動係数(apy_cv)が閾値(1.0)超 → 除外
- 期間中にTVLがピークから50%超下落した(取り付け騒ぎ的な動き。終値だけでは検知できない) → 減点
- `src/risk.py`(DeFiLlamaの`/protocols`・`/hacks`)で、直近730日以内に**そのプールと同じ
  チェーン**でハック被害が確認された → 除外(チェーン不明の記録は全チェーンに保守的に適用)
- それより前のハック歴がある(=一度ハックされたが以降ずっと稼働している) → 除外はしないが
  大きく減点(0.3倍)
- 監査実績が少ない、または稼働歴が浅い(90日未満/不明) → 減点

(`/protocols`の`id`はバージョンごとに別々に振られており、同じidを複数バージョンが共有する
ことは無いため、旧バージョンのハックが別バージョンに誤って波及することは無い。確認済み。)

`src/backtest.py` は、この判定に実際に予測力があるかをウォークフォワード検証する。各プールの
既存履歴データ内で判定時点を15日刻みでずらしながら、「直近30日で判定 → 次の30日の実現値を見る」
を繰り返し、"risky"判定と後半の実現ボラティリティ・TVL下落の相関を、四半期別にも見る。直近の
検証(311フォールド、20プール、11四半期)では、risky判定された方の後半apy_cvが平均1.09
(vs okの0.19)、TVL最大下落幅が平均-0.25(vs okの-0.16)で、大半の四半期で同じ傾向が見られた。
ただし各プールの公開履歴の範囲内での検証であり、複数の強気/弱気相場をまたいだものではない。

`src/scoring.py`実行時には、スコア上位プールへの配分案(`allocate_portfolio`)も出力される。
単一プールの上限20%・単一プロトコルの上限35%・単一チェーンの上限40%を超えないよう、超過分は
他へ比例配分し直す(プロトコル上限の方をチェーン上限より厳しくしているのは、単一チェーンの
障害よりも単一プロトコルのコントラクトバグの方がありふれたリスクという判断だが、厳密な
数値根拠はなく目安)。あくまで案であり、実際の送金・スワップは行わない。

### スナップショットの自動蓄積

`src/backtest.py`のウォークフォワード検証はDeFiLlamaの提供履歴(プールごとに最大2年半程度)
の範囲に限られる。自前で時系列を蓄積すれば、より長期・複数の相場局面をまたいだ本来の
バックテストができるようになるため、`src/snapshot.py`が`analyze_top_candidates()`の結果に
日時を付けて`data/snapshots/YYYY-MM-DD.csv`へ保存する(`load_snapshots()`で結合読み込み可能)。

Windowsタスクスケジューラに毎日08:00実行で登録済み(タスク名: `DefiYieldOptimizerSnapshot`、
`scripts/run_snapshot.bat`を実行、ログは`data/snapshot.log`)。

```bash
schtasks /query /tn "DefiYieldOptimizerSnapshot" /v /fo list   # 状態確認
schtasks /delete /tn "DefiYieldOptimizerSnapshot" /f           # 削除する場合
```

## 注意

- スマートコントラクトリスク、ステーブルコインのデペッグリスク、プロトコルのハッキングリスクは
  常に存在する。TVLが極端に低い/新しすぎるプロトコルの異常に高いAPYは要注意。
- 監査数・ハック履歴はDeFiLlamaの自己申告データであり完全ではない。除外・減点は安全側に
  倒す設計だが、最終判断の代わりにはならない。
- 秘密鍵・シードフレーズは `.env` にも書かない。ウォレット操作が必要な段階になったら
  ハードウェアウォレットや個別の安全な鍵管理を検討する。
