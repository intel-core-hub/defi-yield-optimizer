# defi-yield-optimizer

複数チェーン/プロトコルの利回り(APY)を横断的に比較し、資金配分を最適化するツール。

## 進め方(段階を踏む)

1. **フェーズ1**: DeFiLlama公開API(`yields.llama.fi`)から読み取り専用でAPYデータを取得・分析。
   ウォレット接続や送金は一切行わない。まずはどのプール/チェーンが安定して高利回りかを
   データで把握する。
2. **フェーズ2**: 過去のAPY推移データを蓄積し、変動リスク(APYの安定性、TVLの増減、
   プロトコルの監査状況・稼働歴・過去のハック有無)を加味したスコアリングモデルを作り、
   単一プール/プロトコルへの集中を避けた配分案を出す。`src/snapshot.py`で判定結果を
   日次蓄積し、より長期のバックテストの材料にする(継続中)。
3. **フェーズ3(小額検証、今ここ)**: 実際の資金移動・スマートコントラクト操作(入金/出金/
   スワップ)はユーザー自身のウォレットで実行する。ツール(Claude Code)側では実行できない
   し、実行すべきでもない。始める前のチェックリスト:
   - `python src/scoring.py`を実行し、**その場で取得した最新データ**で判断する(古いCSVで
     判断しない)。`flag`が`ok`以外(`tvl_drawdown_risk`・`past_hack_risk`など)のプールは
     候補から外す。
   - スコア上位でも、ツールの判定を鵜呑みにせず自分の目で二次確認する: プロトコル公式
     サイト、監査レポート原本、コントラクトアドレスがDeFiLlama記載のものと一致するか。
   - まずテストネット、それが難しければ「全部失っても困らない」額のみで少額実行する。
   - 送金・入金・スワップは自分のウォレット(MetaMask等)で行う。秘密鍵・シードフレーズは
     コードにも`.env`にも書かない。
   - 入金後も`src/snapshot.py`(自動蓄積)や`src/scoring.py`を定期的に見て、スコア・
     監査状況・フラグに変化がないか監視する。
   - 最低でも数週間は少額のまま保有し、想定通りのAPY/TVLの動きになっているか確認して
     から増額を検討する。焦って一気に増やさない。

## セットアップ

```bash
python -m venv .venv
.venv/Scripts/pip install -r requirements.txt
python src/yields.py     # 全プールのAPYスナップショット
python src/scoring.py    # 上位候補の履歴を取得し、安定性・プロトコルリスクを加味してスコアリング+配分案
python src/scoring.py 50000  # 上記+投入予定額(円)を渡すとガス代/ポジション比率の目安も出す
python src/risk.py       # 監査数/稼働歴/過去のハック有無だけを単体で確認したい場合
python src/backtest.py   # スコアリングの判定に予測力があるかの簡易バックテスト
```

```bash
.venv/Scripts/python -m pytest tests/    # 単体テスト(ネットワーク呼び出しなし)
```

(グローバルのPython環境には依存パッケージが入っていないため、既定のカーネルのままだと動かない)。

`src/scoring.py` は生APYの平均ではなく中央値を使い、以下に該当するプールはスコア対象から
除外(または大きく減点)する。異常に高いAPYは大抵、報酬トークンの一時的な大量エミッションや
薄い流動性による見せかけであり、そのまま鵜呑みにしないための安全弁。

- 変動係数(apy_cv)が閾値(1.0)超 → 除外
- 期間中にTVLがピークから50%超下落した(取り付け騒ぎ的な動き。終値だけでは検知できない) → 減点
- `src/risk.py`(DeFiLlamaの`/protocols`・`/hacks`)で、直近730日以内に**そのプールと同じ
  チェーン**でハック被害が確認された → 除外(チェーン不明の記録は全チェーンに保守的に適用)
- それより前のハック歴がある(=一度ハックされたが以降ずっと稼働している) → 除外はしないが
  大きく減点(0.3倍)
- 監査実績が少ない、またはDeFiLlama掲載からの経過日数(`days_since_defillama_listing`)が
  浅い(90日未満/不明) → 減点。これは「プロトコル実際の稼働歴」そのものではなく、
  DeFiLlamaがそのプロトコルの追跡を開始してからの日数の代理指標である点に注意
  (実際の稼働開始がDeFiLlama掲載より前のことは普通にある)。
- プロトコルのカテゴリが`Uncollateralized Lending`・`RWA Lending`・`RWA` → 除外
  (`EXCLUDED_CATEGORIES`)。借り手・保険引受先など実世界のカウンターパーティに対する
  信用リスクを内包しており、スマートコントラクトが無事でも元本が返ってこない可能性が
  ある。TVL/APYの安定性・監査数・稼働歴のどれを見ても検知できないため、機械的な除外で
  対応する。
- 現在のAPYの80%超(`MAX_TRUSTED_REWARD_SHARE`)が報酬トークン(`apyReward`)由来 → 除外。
  `apy_cv`は合計APYの変動しか見ておらず、緩やかに逓減する報酬発行スケジュールは短い
  観測窓だと「安定している(cv低め)」ように見えてしまう。そのためAPYの構成比
  (ベースAPY vs 報酬APY)自体を`apy_cv`とは独立にチェックする。

(`/protocols`の`id`はバージョンごとに別々に振られており、同じidを複数バージョンが共有する
ことは無いため、旧バージョンのハックが別バージョンに誤って波及することは無い。確認済み。)

(API依存リスク: `/protocols`はDeFiLlamaの公開freeエンドポイント一覧に載っているが、`/hacks`は
本記述時点でその一覧に見当たらない。2026-09-08時点では動いているが、Pro向けAPIとして
案内されている可能性があり、将来予告なく仕様変更・廃止されうる依存として扱うこと。)

各行には`pool_id`(DeFiLlamaのプールUUID)も残る。`chain`/`project`/`symbol`が同じでも
別プールというケースが普通にある(例: 同じ`Monad`の`accountable`・`USDC`でも複数プールが
存在する)ので、実際に資金を入れる段階では`pool_id`で対象を一意に特定すること。

`src/backtest.py` は、この判定に実際に予測力があるかをウォークフォワード検証する。各プールの
既存履歴データ内で判定時点を15日刻みでずらしながら、「直近30日で判定 → 次の30日の実現値を見る」
を繰り返し、"risky"判定と後半の実現ボラティリティ・TVL下落の相関を、四半期別にも見る。直近の
検証(311フォールド、20プール、11四半期)では、risky判定された方の後半apy_cvが平均1.09
(vs okの0.19)、TVL最大下落幅が平均-0.25(vs okの-0.16)で、大半の四半期で同じ傾向が見られた。

ただしこの結果には限界があり、主張を過大に広げないよう注意すること:
- 各プールの公開履歴の範囲内(最大でも2年半程度)での検証であり、複数の強気/弱気相場を
  完全にまたいだものではない。
- 検証している候補は毎回「現在APYが高いプール」上位40件であり、当時APYが低かった/
  存在しなかったプールは母集団に入らない(生存者バイアス/選定時点バイアス)。
- 検証しているのは`stability_metrics()`(apy_cv・TVLドローダウン)のflagのみで、
  監査数・掲載日数・ハック減点まで含めた`composite_score()`全体の予測力ではない。

したがって言えるのは「安定性フィルタ(apy_cv・TVL急減)には予測力の兆候がある」であり、
「このスコアリングモデル全体の予測力を実証した」はまだ言い過ぎ。`src/snapshot.py`で
蓄積している日次スナップショットが数ヶ月分貯まれば、生存者バイアスの無い、
composite_score全体を対象にしたより正確な検証ができるようになる。

`src/scoring.py`実行時には、スコア上位プールへの配分案(`allocate_portfolio`)も出力される。
スコアの高い順に、単一プール上限20%・単一プロトコル上限35%・単一チェーン上限40%に収まる
範囲で貪欲(greedy)に割り当てる(プロトコル上限の方をチェーン上限より厳しくしているのは、
単一チェーンの障害よりも単一プロトコルのコントラクトバグの方がありふれたリスクという
判断だが、厳密な数値根拠はなく目安)。あくまで案であり、実際の送金・スワップは行わない。

(以前は「スコア比例の重みから始め、超過分を比例配分し直す」方式だったが、1つのプールが
複数の上限(例: プロトコル上限とチェーン上限の両方)に同時に抵触するケースで再配分が
振動し、実データでスコアが並程度のプールの重みがほぼ0に潰れる不具合があったため、
振動が原理的に起きない貪欲法に変更した。トレードオフとして、上位候補(既定10件)の
多様性が上限を埋めるのに足りない場合、100%を配分しきれず一部が「未配分」として残る。)

### ガス代/ポジション比率の目安(小額検証で特に重要)

`python src/scoring.py <投入予定額(円)>`のように投入予定額を渡すと、配分案に
`est_gas_jpy`(チェーン別の往復ガス代の粗い目安)・`position_jpy`(その配分での実際の
ポジション額)・`gas_pct_of_position`・`high_gas_cost_warning`(ガス代がポジションの5%
超なら`True`)の列が追加される。小額検証([フェーズ3](#進め方段階を踏む)参照)では、
ポジションが小さいほどガス代の比率が無視できなくなるため、この確認は重要。

ガス代テーブル(`ROUGH_ROUNDTRIP_GAS_JPY`)は為替レート・ネットワーク混雑状況で変わる
手動更新の目安値であり、`GAS_TABLE_REVIEW_INTERVAL_DAYS`(既定90日)を超えて未更新だと
実行時に標準エラー出力へ警告が出る。実際の執行直前には必ずガストラッカーで最新値を
確認すること。

### スナップショットの自動蓄積

`src/backtest.py`のウォークフォワード検証はDeFiLlamaの提供履歴(プールごとに最大2年半程度)
の範囲に限られる。自前で時系列を蓄積すれば、より長期・複数の相場局面をまたいだ本来の
バックテストができるようになるため、`src/snapshot.py`が`analyze_top_candidates()`の結果に
日時を付けて`data/snapshots/YYYY-MM-DD.csv`へ保存する(`load_snapshots()`で結合読み込み可能)。

Windowsタスクスケジューラに毎日08:00実行で登録済み(タスク名: `DefiYieldOptimizerSnapshot`、
`scripts/run_snapshot.bat`を実行、ログは`data/snapshot.log`)。

```bash
schtasks /query /tn "DefiYieldOptimizerSnapshot" /v /fo list   # 状態確認
schtasks /delete /tn "DefiYieldOptimizerSnapshot" /f           # 削除する場合
```

## 注意

- スマートコントラクトリスク、ステーブルコインのデペッグリスク、プロトコルのハッキングリスクは
  常に存在する。TVLが極端に低い/新しすぎるプロトコルの異常に高いAPYは要注意。
- 監査数・ハック履歴はDeFiLlamaの自己申告データであり完全ではない。除外・減点は安全側に
  倒す設計だが、最終判断の代わりにはならない。
- 秘密鍵・シードフレーズは `.env` にも書かない。ウォレット操作が必要な段階になったら
  ハードウェアウォレットや個別の安全な鍵管理を検討する。
- 配布・共有する際は `.venv/` と `.git/` を含めない(`.venv/`だけで数百MB規模になる)。
  `requirements.txt`から`pip install`で再構築できるので、コード一式(`src/`・
  `notebooks/`・`scripts/`・`tests/`・`requirements.txt`・`README.md`)だけで十分。
